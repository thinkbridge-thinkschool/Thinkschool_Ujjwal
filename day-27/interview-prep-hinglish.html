Week 5 — Cloud-native + DevOps: Interview Prep (Hinglish)

23 Bicep IaC

Pura QuoteHub infra Bicep modules me likha — App Service, SQL, Static Web App, Key Vault, App Insights, Service Bus, VNet. Alag dev aur prod parameter files, aur har cost-wala decision platform ke actual free tiers dekh ke justify kiya gaya.

Theory

Bicep kya hai, aur raw ARM JSON ya Terraform ke upar kyun use kiya?

Bicep ek domain-specific language hai jo ARM JSON me transpile hota hai — matlab ye koi naya deployment engine nahi hai, bas ARM ke upar ek zyada readable authoring layer hai. Har Bicep file compile hoke wahi JSON template banati hai jo ARM hamesha se accept karta aaya hai (az bicep build se ye khud confirm ho jaata hai).

Raw ARM JSON ke against: modules, string interpolation, type-checking, aur ek linter milta hai — deeply nested JSON aur [concat(...)] jaise functions ki jagah.

Terraform ke against: Bicep sirf Azure ke liye hai aur iska koi separate state file nahi hota — ARM khud hi state store hota hai (resource group ki deployment history se, ya Deployment Stack se — Day 24 dekho). Terraform multi-cloud hai lekin apna state management khud manage karna padta hai (backend, locking, drift reconciliation - sab apna responsibility).

Modules, parameters, variables, outputs explain karo — ye sab kaise saath me kaam karte hain?

Parameters deploy time pe diye jaane wale inputs hote hain (ek .bicepparam file se ya CLI flags se). Variables template ke andar compute hote hain. Outputs woh values hain jo ek template deployment ke baad expose karta hai — ek child module ka output parent template me doosre resources me wire ho sakta hai.

Real example — main.bicep ko pata nahi hota Static Web App ka hostname jab tak wo create na ho jaaye, isliye CORS module ke output se hi wire kiya jaata hai:

corsAllowedOrigin: 'https://${staticWebApp.outputs.defaultHostname}'

Matlab CORS kabhi bhi hand-type ya guess nahi kiya jaata — ye structurally hi impossible hai ki real hostname se alag ho jaaye.

Bicep me resource ya module ko conditional kaise banate hain?

if (...) expression resource/module declaration ke baad lagta hai. Do real examples is project se:

module serviceBus 'modules/servicebus.bicep' = if (deployServiceBus) { ... }

module sql 'modules/sql.bicep' = if (deploySql) { ... }

Doosra wala Day 28 ke dev/prod database-sharing wale kaam se hai: jab deploySql false hota hai, module simply chalta hi nahi, aur connection string ek pehle se existing server se compute ho jaata hai. Conditional module ka symbol type module | null ban jaata hai, jisko compiler warning BCP318 deta hai agar aap uske outputs unconditionally read karo — fix hai safe-dereference + coalesce pattern, manual ternary nahi (compiler ternary ke through type narrow nahi karta jaise .? se karta hai):

output sqlServerFqdn string = sql.?outputs.?serverFqdn ?? sharedSqlServerFqdn
SQL firewall rules array me Bicep loop kaise use hua hai?

Ek for expression array parameter ke upar, har array element ke liye ek resource:

resource rules 'Microsoft.Sql/servers/firewallRules@2023-08-01-preview' = [
  for rule in firewallRules: {
    parent: server
    name: rule.name
    properties: {
      startIpAddress: rule.startIpAddress
      endIpAddress: rule.endIpAddress
    }
  }
]

Bas ek alag array pass karna kaafi hai rules add/replace karne ke liye (Day 27 me ek named-IP rule add hua; Day 28 me IP change hone pe rotate hua) — resource block duplicate karne ki zaroorat nahi.

@secure() kis liye hai, aur SQL password actually kahan se aata hai?

@secure() ek parameter ko secret mark karta hai — Azure uska value plaintext me deployment history/activity logs me nahi likhega. Ye khud se koi encryption nahi karta; bas value ko plaintext deployment logs me record hone se rokta hai.

Password khud kabhi kisi .bicepparam file me literal nahi hota — har environment Bicep ke getSecret() function ka use karta hai, jo value ko deployment time pe Key Vault se khींch ke laata hai:

param sqlAdministratorPassword = getSecret('<sub-id>', 'rg-thinkschool-day17', 'kv-quoteshub-dev2', 'sql-admin-password')

Real gotcha jo mushkil se pata chala: iske liye target vault me enabledForTemplateDeployment: true hona zaroori hai — ye ek alag, non-obvious setting hai RBAC role se bilkul different. Bina iske, ARM ka apna deployment engine (aapka user identity nahi) secret resolve karte waqt 403 leta hai, ek bahut specific error ke saath: "Access denied to first party service".

24 Deployment Stacks + azd

Plain az deployment group create se Deployment Stacks pe shift kiya — ek resource jo "ye template kya-kya manage karta hai" ko ek group ki tarah track karta hai, saath me real deletion protection ke saath. Iske aas paas azd (Azure Developer CLI) hooks wire kiye.

Theory

Deployment Stacks kaunsi problem solve karte hain jo plain deployment nahi karti?

Ek plain az deployment group create resources create/update to kar deta hai lekin ise koi yaad nahi rehta ki "ye deployment in resources ko own karta hai." Agar aap template se ek resource hata do aur redeploy karo, ARM us orphan resource ko waise hi chhod deta hai — kuch bhi track nahi karta ki wo pehle is template ka part tha.

Ek Deployment Stack khud apna resource type hai (Microsoft.Resources/deploymentStacks) jo ek live "managed resources" list maintain karta hai, aur har deploy pe reconcile karta hai: template se kuch hatao, aur stack us ab-unmanaged resource ko automatically detach ya delete kar sakta hai.

actionOnUnmanage explain karo — teen options kya hain aur is project ne detachAll kyun choose kiya?
  • deleteAll — template se hataye gaye resources actually delete ho jaate hain
  • deleteResources — resources delete hote hain lekin resource groups/management groups rakhe jaate hain
  • detachAll — stack us resource ko track karna band kar deta hai, lekin Azure me wo waise ka waisa chhod diya jaata hai, touch nahi hota

detachAll safe default hai kisi bhi cost-sensitive ya real-data-wali cheez ke liye: Bicep file se ek line hatana kabhi bhi DROP DATABASE chalane jaisa nahi hona chahiye. Agar koi resource genuinely delete karna hai, to wo ek deliberate, alag action hona chahiye — template edit karne ka side-effect nahi.

denySettings kya hai, aur denyDelete actually kya block karta hai?

denySettings ek Azure deny assignment apply karta hai (ye RBAC role assignment se alag hai — ye ek explicit block hai, RBAC se alag evaluate hota hai) us stack ke saare managed resources pe. denyDelete delete (aur, mode ke hisaab se, kuch writes) ko kisi ke bhi liye block karta hai, deploying principal sameत — sirf stack ke through hi ho sakta hai. applyToChildScopes: true isko child resources tak extend karta hai (jaise SQL server ke firewall rules).

Ye actually verify hua hai, sirf padha nahi gaya: ek stale rule ko direct az sql server firewall-rule delete se hatane ki koshish DenyAssignmentAuthorizationFailed se reject ho gayi, aur uss exact deployment stack ka naam bhi bataya jisne deny assignment banaya tha — proof ki protection genuinely live hai, sirf theory nahi.

azd (Azure Developer CLI) kya hai, aur Bicep files se iska kya relation hai?

azd ek higher-level CLI hai jo provisioning (Bicep/Terraform) aur app deployment dono ko ek command (azd up) ke peeche wrap kar deta hai, jo azure.yaml se drive hota hai. Isme lifecycle hooks support hote hain — scripts jo specific points pe chalte hain (pre/post-provision, pre/post-deploy). Is project ki actual stack-creation logic azd ki native provisioning ki jagah ek hook script me rehti hai, kyunki jab ye kaam hua tab azd ki built-in provisioning Deployment Stacks ke specific flags support nahi karti thi — hook hi actually az stack group create ko sahi settings ke saath call karta hai.

25 Identity end-to-end

JWT signing key ko App Service settings se poora nikaal ke Key Vault me daala, jo Web App ke apne system-assigned managed identity se runtime pe resolve hota hai — ab kisi bhi app setting me koi secret nahi hai, kabhi nahi. Koi standalone day-25/ folder main branch pe nahi hai — ye kaam day-23/modules/keyvault.bicep + keyvaultaccess.bicep me rehta hai (iska apna README day25-identity branch pe hai, kabhi merge nahi hua).

Theory

System-assigned vs. user-assigned managed identity — is project ne kaunsa use kiya, aur kyun?

System-assigned: resource ke lifecycle se 1:1 juda hota hai — Web App ke saath banta hai, uske saath delete hota hai. User-assigned: ek standalone identity resource jo multiple resources me share ho sakta hai aur kisi ek se zyada time tak rehta hai.

Ye project system-assigned use karta hai (identity: { type: 'SystemAssigned' } Web App pe) — sirf ek App Service hai jisko sirf ek identity chahiye, koi sharing requirement nahi hai, isliye simpler, auto-lifecycle-managed option hi sahi choice hai. Live confirm kiya: az webapp identity show return karta hai "type": "SystemAssigned" ek real principalId ke saath.

RBAC authorization vs. Key Vault access policies — actual difference kya hai, aur enableRbacAuthorization: true se kya change hota hai?

Legacy access policy model ek vault-specific ACL hai, jo Azure ke general RBAC system se bilkul invisible/unrelated hai. RBAC mode vault permissions ko ordinary Azure role assignments (Microsoft.Authorization/roleAssignments) bana deta hai, vault pe scoped — wahi mechanism jo Azure me har jagah use hota hai, auditable aur manageable exactly waise hi jaise koi bhi doosra resource.

Real, load-bearing consequence: RBAC-mode vault kisi ko bhi default access nahi deta, khud ke creator ko bhi nahi. Is project me jab bhi naya vault bana (Day 25, 27, 28), agla step hamesha role grant karna tha — sirf create command kabhi kaafi nahi tha.

Vault pe "aapka user account" aur "app ka identity" ke beech least-privilege split kya hai?

Do alag roles, deliberately:

  • Key Vault Secrets Officer (secrets read + write) — human operator ko diya jaata hai, temporarily, taaki az keyvault secret set se actually secret values populate kar sake.
  • Key Vault Secrets User (sirf secret values read kar sakta hai — built-in role 4633458b-17de-408a-b874-0445c86b69e6) — App Service ke managed identity ko diya jaata hai. Ye kabhi bhi secret write nahi kar sakta, vault manage nahi kar sakta, ya keys/certificates ko touch nahi kar sakta.

Current vault pe live confirm kiya:

$ az role assignment list --scope .../vaults/kv-quoteshub-dev2
Principal          Role
------------------ -------------------------
User                Key Vault Secrets Officer
ServicePrincipal    Key Vault Secrets User
App Service runtime pe Key Vault reference ko actually kaise resolve karta hai — mechanism kya hai?

Ek app setting value jo special form me hai @Microsoft.KeyVault(SecretUri=...), App Service platform khud ise recognize karta hai (aapka code nahi). Runtime pe, platform site ke managed identity ka use karke real secret value Key Vault se fetch karta hai aur substitute kar deta hai — aapka application code sirf IConfiguration["Jwt:Key"] ko ek ordinary string ki tarah padhta hai aur kabhi bhi reference syntax nahi dekhta ya Key Vault se directly baat nahi karta.

Practical / coded — ek real production incident sameत

Wo exact Bicep dikhao jo Key Vault reference string banata hai.

day-23/modules/appservice.bicep se:

param keyVaultUri string
param jwtKeySecretName string = 'jwt-key'
...

Notice karo ki ye ek plain string hai jo deploy time pe banti hai — actual secret value kabhi is parameter, template, ya kisi bhi deployment log se hoke nahi guzarti. Sirf ek URI guzarta hai.

keyvault.bicep aur keyvaultaccess.bicep do alag modules kyun hain, ek kyun nahi?

Ek circular dependency todne ke liye: role assignment ko App Service ka principalId chahiye (jo sirf appservice.bicep chalne ke baad milega), jabki appservice.bicep ko vault ka URI chahiye (jo sirf vault banne ke baad milega). Agar role assignment vault module ke andar hota aur principalId ko parameter ki tarah leta, to poora vault module (vault creation sameत) App Service ka wait karta, jo khud vault ka wait karta — ek genuine cycle. Do alag modules, jo main.bicep independently wire karta hai, isse bachaate hain.

Real incident: ek Key Vault reference MSINotEnabled dikha raha tha jabki identity clearly exist karti thi. Kya galat tha, aur actually fix kaise hua?

Deployment ke baad, az webapp identity show pehle se real principalId return kar raha tha, aur app setting bhi correct reference string dikha raha tha — lekin resolution status directly query karne pe ye dikha:

GET .../config/configreferences/appsettings
"status": "MSINotEnabled",
"details": "Reference was not able to be resolved because site Managed Identity not enabled."

Do full app restarts aur kai minute ka polling kuch change nahi hua. Actual fix, Microsoft ki apni docs me isi exact symptom ke liye mila: App Service Key Vault reference resolutions ko cache karta hai, aur config change hamesha reliable re-fetch trigger nahi karta. Ek direct POST refresh endpoint pe turant fix kar deta hai:

POST /subscriptions/{sub}/resourceGroups/{rg}/providers/Microsoft.Web/sites/{site}/config/configreferences/appsettings/refresh?api-version=2022-03-01

Interview-ready takeaway: agar identity aur role assignment genuinely sahi confirm karne ke baad bhi Key Vault reference MSINotEnabled dikhaye, restart karte mat raho — refresh endpoint ko call karo.

Kya ek direct out-of-stack write (jaise az webapp identity assign) denyDelete se block ho jaata?

Nahi — denyDelete deletes block karta hai, writes nahi. Identity assignment ya app-setting change ek write hai, isliye ye directly through ho jaata. Stack se hi route karne ki asli wajah ye nahi hai ki "ye fail ho jaata" — wajah ye hai ki direct write tik nahi paata: agla plain az stack group create ise silently wapas wahi kar deta jo main.bicep kehta hai, kyunki stack (live resource nahi) hi source of truth hai. Interview me ye precisely bolne wali baat hai — "denied" aur "not durable" ko confuse karna easy mistake hai.

26 App Insights + KQL

Workspace-based Application Insights end-to-end wire kiya, ek real trace-context propagation bug fix kiya jo ek async boundary ke across tha (HTTP request → background outbox worker), aur real KQL live traffic pe likha/chalaya.

Theory

Workspace-based vs. classic Application Insights — aaj sirf ek hi option kyun hai?

Classic (non-workspace) App Insights nayi resources ke liye retire ho chuka hai — workspace-based hi ek option hai, preference nahi. Is mode me, ek Log Analytics workspace actual data store hota hai; App Insights component ek thin view/API surface hai us hi workspace data ke upar, connection string ke saath.

operation_Id kya hai, aur ek trace ko background worker ke across actually "stitch" kaise hota hai?

operation_Id distributed-tracing correlation ID hai jo ek logical operation ke saare telemetry items share karte hain (underneath ek W3C traceparent). Ek same-process HTTP request ise automatically Activity.Current se share karta hai — lekin ek async boundary cross karte hi (ek value database me abhi likhi jaati hai, kisi doosre process/thread me baad me padhi jaati hai), wo ambient context gayab ho jaata hai jab tak explicitly capture aur restore na karo.

Is project ke outbox pattern ko exactly yehi chahiye tha: outbox row likhte waqt trace ID capture karo, use data ki tarah store karo, aur jab background relay baad me us row ko process kare tab use parent context ki tarah restore karo.

percentile() aapko kya batata hai jo avg() nahi batata, aur ye yahan kyun matter karta hai?

Average ek heavy tail poori tarah chhupa sakta hai — ek slow request aur nau fast requests ek "average" bana sakte hain jo theek dikhta hai jabki p99 ek real problem dikha raha ho. Is project se real evidence: sirf n=3 pe hi, POST /api/quotes ne p50 = 2546ms vs p99 = 5679ms dikhaya — 2x se zyada apart — ye gap jo average akela ek misleading number me flatten kar deta.

Practical / coded — real KQL, live data pe chalaya

Query: request → dependency → dependency across operation_Id se ek pura trace stitch karo. 
union requests, dependencies, traces
| where operation_Id == '1b34db74478abf6227eaf579dd4389c1'
| project timestamp, itemType, name, message, duration, resultCode, severityLevel
| order by timestamp asc

Real result: ek 3-level trace — POST /api/quotes/ (5679.5ms) → ProcessOutboxMessage (11754.5ms, ek background dependency) → ek SQLite write (26.4ms) uske andar nested — sab ek hi operation_Id share karte hue, proof ki trace-context fix actually end to end kaam kar raha hai.

Query: endpoint ke hisaab se p50/p99 duration. 
requests
| where timestamp > ago(1h)
| summarize count = count(), p50 = percentile(duration, 50), p99 = percentile(duration, 99) by name
| order by p99 desc
Query: per-request self-time vs. dependency-time — aur chalate waqt mila ek real limitation. 
requests
| where timestamp > ago(1h)
| project operation_Id, requestName = name, requestDuration = duration
| join kind=leftouter (
    dependencies | where timestamp > ago(1h)
    | summarize dependencyDuration = sum(duration), dependencyCount = count() by operation_Id
  ) on operation_Id
| extend dependencyDuration = coalesce(dependencyDuration, 0.0), dependencyCount = coalesce(dependencyCount, 0)
| extend selfDuration = requestDuration - dependencyDuration
| project requestName, requestDuration, dependencyDuration, selfDuration, dependencyCount
| order by requestDuration desc
Real, disclosed limitation: POST /api/quotes/ row ne selfDuration = -6101ms dikhaya — jo nonsensical hai. Wajah: ProcessOutboxMessage operation_Id se correctly link hota hai, lekin request already return hone ke baad chalta hai, uske andar nested nahi. Same-operation_Id ke saare dependencies sum karna sirf genuinely synchronous, in-request kaam ke liye sense banaता hai. Real fix ek time-window guard add karta (dependency timestamp [request.timestamp, request.timestamp + request.duration] ke andar) — ye ek achha interview answer hai jo dikhata hai ki aap query ka blind spot jaante ho, ek plausible-lagne-wale result ko blindly trust nahi karte.
Query: actual error-rate alert condition, aur 10-request floor kyun matter karta hai. 
requests
| where timestamp > ago(5m)
| summarize total = count(), serverErrors = countif(toint(resultCode) >= 500)
| where total >= 10
| extend errorRatePercent = todouble(serverErrors) / total * 100
| where errorRatePercent > 5

Do gotchas jo bolne layak hain: resultCode ek string column hai — bina toint() ke 500 se compare karo to SEM0064 se fail hota hai (actually chalake pata chala). Aur total >= 10 floor isliye hai taaki 2 total requests me 1 failure (ek statistically meaningless 50%) is alert ko quiet API pe fire na kar sake.

27 Security pass

Actual live system ke against STRIDE threat model, real rate limiting ship kiya, ek real information-disclosure bug dhoonda aur fix kiya, aur ZAP scan pe honest "not run" bola jab disk space ki wajah se unsafe tha.

Theory

STRIDE ke chhe categories batao, aur is project se har ek ka ek real example do.
  • Spoofing — registration pe koi email verification nahi hai; koi bhi victim@realcompany.com ki tarah register kar sakta hai
  • Tampering — [MaxLength] attributes silently unenforced the (Minimal APIs automatically DataAnnotations validate nahi karte jaise [ApiController] MVC karta hai)
  • Repudiation — "kisne kya delete kiya" ka koi structured audit trail nahi hai, sirf usी waqt ka ek ownership check hai
  • Information Disclosure — createdBy (ek real email) fully anonymous GET /api/quotes se return ho raha tha
  • Denial of Service — kahin bhi rate limiting nahi thi, ek App Service pe jiska hard 60 CPU-minutes/day quota hai (F1 tier)
  • Elevation of Privilege — har authenticated user ko login pe unconditionally saare teen scopes mil jaate hain (read/write/delete) — koi privilege tier exist hi nahi karta
Fixed-window vs. sliding-window rate limiting — is project ne kaunsa use kiya, aur trade-off kya hai?

ASP.NET Core ka built-in fixed-window limiter use kiya (Microsoft.AspNetCore.RateLimiting, koi naya dependency nahi). Trade-off: fixed window boundary pe ek burst allow kar sakta hai (jaise ek window ke last second me 5 requests, agle window ke first second me 5 aur — ~2 seconds me 10). Sliding window ise smooth kar deta hai lekin track karne me zyada cost lagti hai. Is scale ke login endpoint ke liye, fixed-window ki simplicity sahi choice thi — honestly ek real, accepted limitation ki tarah likha gaya, over-engineer nahi kiya gaya.

IP ke hisaab se rate limiter partition karne ke liye App Service pe specifically UseForwardedHeaders() kyun chahiye?

Iske bina, App Service pe HttpContext.Connection.RemoteIpAddress platform ka internal front-end address return karta hai — har caller ek hi partition me aa jaata — matlab ek abusive user baaki saare legitimate users ko rate-limit kar sakta tha jo API share karte hain. UseForwardedHeaders (jo X-Forwarded-For trust karta hai) pipeline me jaldi chalna chahiye — rate limiter se pehle, aur request logging se bhi pehle — taaki downstream middleware real caller dekhe.

VNet integration ke liye minimum App Service tier kya hai, aur F1 private endpoints kyun use nahi kar sakta?

VNet integration ke liye dedicated-compute tier chahiye — Basic (B1) aur upar; Free/Shared tiers explicitly exclude hain, Microsoft ki apni docs se directly confirm kiya. Real cost, Azure ke retail pricing API se query kiya (guess nahi kiya): East Asia me B1 Linux ke liye $0.02/hour → ~$14.60/month. VNet + private endpoint Bicep waise hi likha gaya (network.bicep) taaki jab kabhi tier upgrade ho, ready rahe — lekin kabhi deploy nahi kiya, kyunki ye ek real recurring cost hai fixed credit ke against.

Practical / coded

Actual rate limiter registration aur policy dikhao.

day-5/QuotesApi/Program.cs se:

builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    options.KnownIPNetworks.Clear();
    options.KnownProxies.Clear();
});

builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    options.AddPolicy("auth", httpContext => RateLimitPartition.GetFixedWindowLimiter(
        partitionKey: httpContext.Connection.RemoteIpAddress?.ToString() ?? "unknown",
        factory: _ => new FixedWindowRateLimiterOptions
