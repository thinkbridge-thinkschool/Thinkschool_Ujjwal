Week 5 — Cloud-native + DevOps: Interview Prep

23 Bicep IaC

Wrote the whole QuoteHub infra as Bicep modules (App Service, SQL, Static Web App, Key Vault, App Insights, Service Bus, VNet) with separate dev and prod parameter files, every cost-sensitive choice justified against the platform's actual free tiers.

Theory

What is Bicep, and why use it over raw ARM JSON or Terraform?

Bicep is a domain-specific language that transpiles to ARM JSON — it's not a new deployment engine, just a much more readable authoring layer on top of the same Azure Resource Manager. Every Bicep file compiles down to the same JSON template ARM has always accepted (az bicep build proves this directly).

Versus raw ARM JSON: modules, string interpolation, type-checking, and a linter, instead of deeply nested JSON with [concat(...)] functions.

Versus Terraform: Bicep is Azure-only and has no separate state file — ARM itself is the state store (via the resource group's deployment history, or a Deployment Stack — see Day 24). Terraform is multi-cloud but needs its own state management (a backend, locking, drift reconciliation you own).

Explain modules, parameters, variables, and outputs — how do they compose?

Parameters are inputs supplied at deploy time (from a .bicepparam file or CLI flags). Variables are computed inside the template. Outputs are values a template exposes after deployment — a child module's outputs become inputs the parent template can wire into other resources.

Real example — main.bicep can't know the Static Web App's hostname until it's created, so CORS is wired using the module's own output:

corsAllowedOrigin: 'https://${staticWebApp.outputs.defaultHostname}'

This means CORS is never hand-typed or guessed — it's structurally impossible for it to drift from the real hostname.

How do you make a resource or module conditional in Bicep?

The if (...) expression after the resource/module declaration. Two real examples from this project:

module serviceBus 'modules/servicebus.bicep' = if (deployServiceBus) { ... }

module sql 'modules/sql.bicep' = if (deploySql) { ... }

The second one is from the Day 28 dev/prod database-sharing work: when deploySql is false, the module simply doesn't run, and the connection string is computed from an already-existing server instead. A conditional module's symbol becomes type module | null, which the compiler flags with warning BCP318 if you try to read its outputs unconditionally — the fix is the safe-dereference + coalesce pattern, not a manual ternary on the same condition (the compiler doesn't narrow types through ternaries the way it does through .?):

output sqlServerFqdn string = sql.?outputs.?serverFqdn ?? sharedSqlServerFqdn
How does the SQL firewall rules array use a Bicep loop?

A for expression over an array parameter, one resource per array element:

resource rules 'Microsoft.Sql/servers/firewallRules@2023-08-01-preview' = [
  for rule in firewallRules: {
    parent: server
    name: rule.name
    properties: {
      startIpAddress: rule.startIpAddress
      endIpAddress: rule.endIpAddress
    }
  }
]

Passing a different array (Day 27 added a named-IP rule; Day 28 rotated the IP when it changed) is enough to add/replace rules — no resource block duplication.

What's @secure() for, and where does the SQL password actually come from?

@secure() marks a parameter as a secret — Azure won't log its value in deployment history/activity logs. It does not encrypt anything by itself; it just suppresses the value from being recorded in plaintext deployment logs.

The password itself is never a literal in any .bicepparam file — every environment uses Bicep's getSecret() function, which pulls the value from Key Vault at deployment time:

param sqlAdministratorPassword = getSecret('<sub-id>', 'rg-thinkschool-day17', 'kv-quoteshub-dev2', 'sql-admin-password')

Real gotcha found the hard way: this requires the target vault to have enabledForTemplateDeployment: true — a separate, non-obvious setting from any RBAC role. Without it, ARM's own deployment engine (not your user identity) gets a 403 trying to resolve the secret, with the very specific error "Access denied to first party service".

Why is the SQL admin login/password module written as a separate sql.bicep, and what would you check if a deploy failed with a naming conflict?

Separation of concerns — main.bicep orchestrates, each module owns one resource type. Real, actually-hit example: SQL server names, Key Vault names, and Web App/Static Web App names are globally unique across all of Azure (not just your subscription). Deploying to a brand-new subscription (Day 27) failed with NameAlreadyExists because the old, expired subscription still held those names — the fix was renaming (sql-quotesapi-thinkschool → ...thinkschool2), not retrying.

24 Deployment Stacks + azd

Moved from plain az deployment group create to Deployment Stacks — a resource that tracks "everything this template manages" as a first-class group, with real deletion protection. Wired azd (Azure Developer CLI) hooks around it.

Theory

What problem do Deployment Stacks solve that a plain deployment doesn't?

A plain az deployment group create creates/updates resources but has no memory of "this deployment owns these resources." If you remove a resource from the template and redeploy, ARM just leaves the orphan sitting there — nothing tracks that it used to be part of this template's output.

A Deployment Stack is its own resource type (Microsoft.Resources/deploymentStacks) that maintains a live "managed resources" list, and reconciles it on every deploy: remove something from the template, and the stack can detach or delete the now-unmanaged resource automatically.

Explain actionOnUnmanage — what are the three options and why did this project pick detachAll?
  • deleteAll — resources removed from the template get actually deleted
  • deleteResources — deletes resources but keeps resource groups/management groups
  • detachAll — the stack stops tracking the resource, but it's left alone in Azure, untouched

detachAll is the safe default for anything cost-sensitive or containing real data: removing a line from a Bicep file should never be the same action as running DROP DATABASE. If a resource genuinely needs deleting, that should be a deliberate, separate action — not a side effect of editing a template.

What is denySettings, and what does denyDelete actually block?

denySettings applies an Azure deny assignment (distinct from a role assignment — it's an explicit block, evaluated separately from RBAC) across every resource the stack manages. denyDelete blocks delete (and, depending on mode, certain writes) on those resources from anyone, including the deploying principal, except through the stack itself. applyToChildScopes: true extends this to child resources (e.g. a SQL server's firewall rules).

This was verified for real, not just read about: an attempt to directly az sql server firewall-rule delete a stale rule was rejected with DenyAssignmentAuthorizationFailed, naming the exact deployment stack that owned the deny assignment — proof the protection is live, not theoretical.

What's azd (Azure Developer CLI), and how does it relate to the Bicep files?

azd is a higher-level CLI that wraps provisioning (Bicep/Terraform) and app deployment behind one command (azd up), driven by azure.yaml. It supports lifecycle hooks — scripts that run at specific points (pre/post-provision, pre/post-deploy). This project's actual stack-creation logic lives in a hook script rather than azd's own native provisioning, because azd's built-in provisioning didn't yet support Deployment Stacks' specific flags at the time — the hook is what actually calls az stack group create with the right settings.

Practical / coded

Write (or read) the real az stack group create command used throughout this project. 
az stack group create \
  --name "quoteshub-dev" \
  --resource-group rg-thinkschool-day17 \
  --template-file main.bicep \
  --parameters params/dev.bicepparam \
  --action-on-unmanage detachAll \
  --deny-settings-mode denyDelete \
  --deny-settings-apply-to-child-scopes \
  --description "..." \
  --yes

Same shape every single time this project touched infrastructure (Days 24 through 28) — proving the settings are a standing policy, not a one-off flag.

How do you inspect what a stack currently manages, and its provisioning state? 
az stack group show --name quoteshub-dev --resource-group rg-thinkschool-day17 \
  --query "{provisioningState:provisioningState, count:length(resources)}"

az stack group show --name quoteshub-dev --resource-group rg-thinkschool-day17 \
  --query "resources[].{id:id, status:status}"

Real example of using this productively: after a partially-failed deploy, checking the managed-resource list (not just the top-level "failed" status) revealed that most resources had actually succeeded — only one module had failed independently, so a retry (rather than a full rebuild) was the right move.

25 Identity end-to-end

Took the JWT signing key out of App Service settings entirely and into Key Vault, resolved at runtime by the Web App's own system-assigned managed identity — no secret in any app setting, ever again. No standalone day-25/ folder on main — this work lives in day-23/modules/keyvault.bicep + keyvaultaccess.bicep (its own README exists on branch day25-identity, never merged).

Theory

System-assigned vs. user-assigned managed identity — which did this project use, and why?

System-assigned: tied 1:1 to the resource's lifecycle — created when the Web App is, deleted when it is. User-assigned: a standalone identity resource that can be shared across multiple resources and outlives any one of them.

This project uses system-assigned (identity: { type: 'SystemAssigned' } on the Web App) — there's exactly one App Service that needs exactly one identity, with no sharing requirement, so the simpler, auto-lifecycle-managed option is the right one. Confirmed live: az webapp identity show returns "type": "SystemAssigned" with a real principalId.

RBAC authorization vs. Key Vault access policies — what's the actual difference, and what does enableRbacAuthorization: true change?

The legacy access policy model is a vault-specific ACL, invisible to (and unrelated to) Azure's general RBAC system. RBAC mode makes vault permissions ordinary Azure role assignments (Microsoft.Authorization/roleAssignments) scoped to the vault — the same mechanism used everywhere else in Azure, auditable and manageable the same way as any other resource's access.

Real, load-bearing consequence: an RBAC-mode vault grants nobody access by default, not even its own creator. Every single time this project created a new vault (Days 25, 27, 28), the very next step had to be granting a role — the create command alone was never enough.

What's the least-privilege split between "my user account" and "the app's identity" on the vault?

Two different roles, deliberately:

  • Key Vault Secrets Officer (read + write secrets) — granted to the human operator, temporarily, to actually populate secret values via az keyvault secret set.
  • Key Vault Secrets User (read secret values only — built-in role 4633458b-17de-408a-b874-0445c86b69e6) — granted to the App Service's managed identity. It can never write a secret, manage the vault, or touch keys/certificates.

Confirmed live on the current vault:

$ az role assignment list --scope .../vaults/kv-quoteshub-dev2
Principal          Role
------------------ -------------------------
User                Key Vault Secrets Officer
ServicePrincipal    Key Vault Secrets User
How does an App Service actually resolve a Key Vault reference at runtime — what's the mechanism?

An app setting value of the special form @Microsoft.KeyVault(SecretUri=...) is recognized by the App Service platform itself (not your code). At runtime, the platform uses the site's managed identity to fetch the real secret value from Key Vault and substitutes it — your application code just reads IConfiguration["Jwt:Key"] as an ordinary string and never sees the reference syntax or talks to Key Vault directly.

Practical / coded — including a real production incident

Show the exact Bicep that builds the Key Vault reference string.

From day-23/modules/appservice.bicep:

param keyVaultUri string
param jwtKeySecretName string = 'jwt-key'
...
{ name: 'Jwt__Key', value: '@Microsoft.KeyVault(SecretUri=${keyVaultUri}secrets/${jwtKeySecretName}/)' }

Notice this is a plain string built at deploy time — the actual secret value never flows through this parameter, the template, or any deployment log. Only a URI does.

Why are keyvault.bicep and keyvaultaccess.bicep two separate modules instead of one?

To break a circular dependency: the role assignment needs the App Service's principalId (only exists after appservice.bicep runs), while appservice.bicep needs the vault's URI (only exists after the vault is created). If the role assignment lived inside the vault module and took principalId as a parameter, the entire vault module would end up waiting on the App Service, which itself waits on the vault — a genuine cycle. Two modules, wired independently by main.bicep, avoids it.

Real incident: a Key Vault reference showed MSINotEnabled even though the identity clearly existed. What was wrong, and how was it actually fixed?

After deployment, az webapp identity show already returned a real principalId, and the app setting already showed the correct reference string — but querying resolution status directly showed:

GET .../config/configreferences/appsettings
"status": "MSINotEnabled",
"details": "Reference was not able to be resolved because site Managed Identity not enabled."

Two full app restarts and several minutes of polling didn't change it. The actual fix, found in Microsoft's own docs for this exact symptom: App Service caches Key Vault reference resolutions, and a config change doesn't always trigger a reliable re-fetch. A direct POST to the refresh endpoint fixes it immediately:

POST /subscriptions/{sub}/resourceGroups/{rg}/providers/Microsoft.Web/sites/{site}/config/configreferences/appsettings/refresh?api-version=2022-03-01

Interview-ready takeaway: if a Key Vault reference reports MSINotEnabled after confirming the identity and role assignment are genuinely correct, don't keep restarting — call the refresh endpoint.

Would a direct out-of-stack write (e.g. az webapp identity assign) have been blocked by denyDelete?

No — denyDelete blocks deletes, not writes. An identity assignment or app-setting change is a write, so it would likely go through directly. The real reason to route it through the stack instead isn't "it would fail" — it's that a direct write wouldn't last: the next plain az stack group create would silently revert it back to whatever main.bicep says, since the stack (not the live resource) is the authoritative source of truth. This is a subtlety worth stating precisely in an interview — conflating "denied" with "not durable" is an easy mistake.

26 App Insights + KQL

Wired workspace-based Application Insights end-to-end, fixed a real trace-context propagation bug across an async boundary (HTTP request → background outbox worker), and wrote/ran real KQL against live traffic.

Theory

Workspace-based vs. classic Application Insights — why only one option today?

Classic (non-workspace) App Insights is retired for new resources — workspace-based is the only option, not a preference. In this mode, a Log Analytics workspace is the actual data store; the App Insights component is a thin view/API surface plus the SDK-facing connection string over that same workspace data.

What is operation_Id, and how does a trace actually get "stitched" across a background worker?

operation_Id is the distributed-tracing correlation ID shared by every telemetry item belonging to the same logical operation (a W3C traceparent under the hood). A same-process HTTP request automatically shares this via Activity.Current — but once you cross an async boundary (a value written to a database now, read back by a different process/thread later), that ambient context is gone unless you explicitly capture and restore it.

This project's outbox pattern needed exactly that: capture the trace ID when the outbox row is written, store it as data, and restore it as the parent context when the background relay later processes that row.

What does percentile() tell you that avg() doesn't, and why does that matter here?

An average can hide a heavy tail entirely — one slow request and nine fast ones can produce an "average" that looks fine while p99 shows a real problem. Real evidence from this project: at just n=3, POST /api/quotes showed p50 = 2546ms vs p99 = 5679ms — over 2x apart — a gap an average alone would have flattened into one misleading number.

Practical / coded — real KQL, run against live data

Query: stitch a full trace by operation_Id across request → dependency → dependency. 
union requests, dependencies, traces
| where operation_Id == '1b34db74478abf6227eaf579dd4389c1'
| project timestamp, itemType, name, message, duration, resultCode, severityLevel
| order by timestamp asc

Real result: a 3-level trace — POST /api/quotes/ (5679.5ms) → ProcessOutboxMessage (11754.5ms, a background dependency) → a SQLite write (26.4ms) nested under it — all sharing one operation_Id, proving the trace-context fix actually worked end to end.

Query: p50/p99 duration by endpoint. 
requests
| where timestamp > ago(1h)
| summarize count = count(), p50 = percentile(duration, 50), p99 = percentile(duration, 99) by name
| order by p99 desc
Query: per-request self-time vs. dependency-time — and a real limitation found while running it. 
requests
| where timestamp > ago(1h)
| project operation_Id, requestName = name, requestDuration = duration
| join kind=leftouter (
    dependencies | where timestamp > ago(1h)
    | summarize dependencyDuration = sum(duration), dependencyCount = count() by operation_Id
  ) on operation_Id
| extend dependencyDuration = coalesce(dependencyDuration, 0.0), dependencyCount = coalesce(dependencyCount, 0)
| extend selfDuration = requestDuration - dependencyDuration
| project requestName, requestDuration, dependencyDuration, selfDuration, dependencyCount
| order by requestDuration desc
Real, disclosed limitation: the POST /api/quotes/ row showed selfDuration = -6101ms — nonsensical. Cause: ProcessOutboxMessage is correctly linked by operation_Id, but runs after the request already returned, not nested within it. Summing every same-operation_Id dependency only makes sense for genuinely synchronous, in-request work. The real fix would add a time-window guard (dependency timestamp within [request.timestamp, request.timestamp + request.duration]) — a good interview answer about knowing a query's blind spot rather than trusting a plausible-looking result blindly.
Query: the actual error-rate alert condition, and why the 10-request floor matters. 
requests
| where timestamp > ago(5m)
| summarize total = count(), serverErrors = countif(toint(resultCode) >= 500)
| where total >= 10
| extend errorRatePercent = todouble(serverErrors) / total * 100
| where errorRatePercent > 5

Two gotchas worth naming: resultCode is a string column — comparing it to 500 without toint() fails with SEM0064 (found by actually running it). And the total >= 10 floor exists so 1 failure out of 2 total requests (a statistically meaningless 50%) can't fire the alert on a quiet API.

27 Security pass

STRIDE threat model against the actual live system, real rate limiting shipped, a real information-disclosure bug found and fixed, and an honest "not run" on the ZAP scan when disk space made it unsafe.

Theory

Name the six STRIDE categories and give one real example of each from this project.
  • Spoofing — no email verification on registration; anyone can register as victim@realcompany.com
  • Tampering — [MaxLength] attributes were silently unenforced (Minimal APIs don't auto-validate DataAnnotations the way [ApiController] MVC does)
  • Repudiation — no structured "who deleted what" audit trail beyond an in-the-moment ownership check
  • Information Disclosure — createdBy (a real email) was returned by the fully anonymous GET /api/quotes
  • Denial of Service — no rate limiting anywhere, on an App Service with a hard 60 CPU-minutes/day quota (F1 tier)
  • Elevation of Privilege — every authenticated user is granted all three scopes (read/write/delete) unconditionally at login — no privilege tier exists at all
Fixed-window vs. sliding-window rate limiting — which did this project use, and what's the trade-off?

Used ASP.NET Core's built-in fixed-window limiter (Microsoft.AspNetCore.RateLimiting, no new dependency). Trade-off: a fixed window can allow a burst right at the boundary (e.g. 5 requests in the last second of one window, 5 more in the first second of the next — 10 in ~2 seconds). A sliding window smooths this out but costs more to track. For a login endpoint at this scale, fixed-window's simplicity was the right call — named honestly as a real, accepted limitation rather than over-engineered away.

Why does partitioning a rate limiter by IP require UseForwardedHeaders() on App Service specifically?

Without it, HttpContext.Connection.RemoteIpAddress on App Service returns the platform's internal front-end address — every caller would land in the same partition, meaning one abusive user could rate-limit every other legitimate user sharing the API. UseForwardedHeaders (trusting X-Forwarded-For) must run early in the pipeline — before the rate limiter and before request logging — so downstream middleware sees the real caller.

What's the minimum App Service tier for VNet integration, and why can't F1 use private endpoints?

VNet integration requires a dedicated-compute tier — Basic (B1) and above; Free/Shared tiers are explicitly excluded, confirmed directly against Microsoft's own docs. Real cost, queried from Azure's retail pricing API (not guessed): $0.02/hour for B1 Linux in East Asia → ~$14.60/month. The VNet + private endpoint Bicep was written anyway (network.bicep) so it's ready the moment the tier is upgraded — but never deployed, since it's a real recurring cost against a fixed credit.

builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;

{

        factory: _ => new FixedWindowRateLimiterOptions

            PermitLimit = 5,
            Window = TimeSpan.FromMinutes(1),
            QueueLimit = 0,

});

Show the createdBy redaction fix — and explain why it maps over the data instead of mutating it in place. 
private static object RedactIfAnonymous(Quote quote, ClaimsPrincipal user) =>
    user.Identity?.IsAuthenticated == true
        ? quote
        : new { quote.Id, quote.Author, quote.Text, CreatedByUserId = (string?)null, CreatedBy = (string?)null };

The list handler's quotes variable can be a HybridCache-cached, shared instance reused across concurrent callers. Mutating the cached objects in place would leak the redaction into (or wrongly hide it from) a different caller depending on request timing — the cache must keep storing the full truth, with each response filtered fresh based on the current caller only.

What was wrong with the original ExceptionMiddleware, and what's the fix?

It returned the raw ex.Message in the 500 response body in every environment, including production — a real information-disclosure vector (file paths, connection details, internal type names can end up in an exception message). Fix: gate the detail on environment, keep logging the full exception server-side either way:

Detail = _env.IsDevelopment() ? ex.Message : "An unexpected error occurred. Please try again later."
Confirm every endpoint's authorization was actually verified, not assumed — how?

By reading the whole EndpointExtensions.cs file directly rather than trusting memory or naming conventions. Result: GET /api/quotes and GET /api/quotes/{id} are anonymous by deliberate design (documented in a code comment); every mutating endpoint (POST/DELETE on quotes and collections) carries .RequireAuthorization(...), and DELETE/item-removal additionally check resource ownership via a custom IAuthorizationHandler. Also confirmed no global fallback auth policy exists — anonymous endpoints are anonymous by explicit design, not by an accidental absence of a default-deny.
